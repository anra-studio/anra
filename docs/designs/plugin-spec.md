# Plugin Spec

状态：设计草案。Plugin 机制与接口尚未实现。

本规范定义 Anra 如何注册、配置和调用 integration plugin。应用接入、角色交接与
Tape 记录的行为见 [Plugin Integration Spec](plugin-integration-spec.md)；外部执行端
读取角色上下文的接口见 [Anra MCP Spec](anra-mcp-spec.md)。

## 责任边界

Plugin 是 Anra 的应用接入扩展。它将应用接口转换为 Anra 可使用的操作和观察结果。
Plugin 不是 Peer；角色仍使用自己的 Peer 身份。一个应用可以同时作为交互入口和
外部执行环境，两种用途各自声明能力，并通过明确的角色绑定启用。

Anra 核心拥有 Role、Peer、RoleBinding、交接 anchor、上下文授权、Tape 写入及角色执行。
Plugin 拥有具体应用的连接、目标解析、请求映射、状态解释及来源记录转换。Plugin
不能直接绕过核心写 Tape，也不自行扩大上下文访问范围。Anra MCP 是核心服务，
plugin 不拥有该服务的定义或授权策略。

## 注册与连接

首版显式注册内置 plugin，由 composition 层按配置创建和关闭，不要求动态加载、
跨进程插件协议或插件市场。每种 plugin 有稳定的类型 ID 和契约版本；同一类型可
有多个独立的 PluginConnection。连接包含稳定 ID、配置、凭据引用、启用的能力和
运行状态。凭据不出现在 Role、prompt、Tape 或 plugin 的公开能力描述中。

连接在启动时校验配置，初始化所需客户端并发现能力；不可用或授权失效时保留
可诊断的状态，不将 unknown 当作 offline。关闭时停止接收新工作、释放连接；
外部工作是否继续由该应用的契约决定，不能仅凭本地连接关闭推断取消。

核心以连接 ID 与 RoleBinding 选择目标；plugin 使用已授权的目标引用，不靠显示
名称猜测角色、机器或项目。第三方标识由所属 plugin 解释，核心持久化并原样路由。
单一传输协议不意味着具体应用具有相同的执行语义。

## 调用上下文

核心调用 plugin 时，通过 `ctx` 携带本次操作的 Role 和已授权的 RoleBinding，
以及对应的 PluginConnection 身份。`ctx` 是作用域明确的调用上下文：Role 标识
角色，RoleBinding 标识此次操作的应用目标及用途；同一 Role 的不同绑定不能互换。
需要关联某次外部工作的操作，还应携带交接 anchor 引用。任务内容、外部执行引用及
观察结果仍作为各操作的输入或输出，不放进通用上下文。

`ctx` 由核心在解析绑定、检查连接和授权后构造，plugin 使用其中的绑定解析应用
目标，不以外部传入的角色名或绑定信息作为授权依据。入站消息在认证来源并解析到
绑定之前没有可信的 Role 或 RoleBinding；plugin 先报告来源，核心解析后再建立
对应的 `ctx`。异步观察或恢复时，核心根据持久化的绑定和交接 anchor 重新建立调用
上下文，不依赖原调用仍在运行。凭据不放入 `ctx` 或写入 Tape。

这里的 `ctx` 描述逻辑契约；具体实现可以用显式类型承载角色和绑定，并与负责
取消和超时的运行时 context 配合，不要求将领域数据放入隐式键值存储。

## 能力契约

能力按连接和目标检查。实际可用能力取 plugin 支持、应用运行状态、授权和本地
启用状态的交集。下表描述逻辑操作，不规定 Go 接口或网络格式：

| 能力 | Plugin 对核心的行为 |
| --- | --- |
| 接收消息 | 将已认证的应用消息转换为带来源和目标绑定的输入 |
| 发送回复 | 向已验证的来源会话或指定目标发送结果，并返回投递状态 |
| 提交外部工作 | 接收目标、任务和上下文引用，返回接受状态及外部执行引用 |
| 延续工作 | 向已关联的外部会话提交新的工作，并保留此次执行引用 |
| 观察与恢复 | 交付可观察记录、状态、来源标识、可见范围及可恢复进度 |
| 取消 | 请求取消并返回结果；请求已接受不表示外部工作已停止 |

实现可只支持其中一部分。核心在外部副作用前检查调用所需能力，不自动更换目标。
能力变化、限流、认证失败、未知结果和明确拒绝应可区分；调用方可以据此决定
是否等待、对账或终止。交互入口和外部执行的消息形态不同，不强行归并成同一个
通用执行操作。

## 观察记录与持久化

Plugin 向核心提供规范化观察记录：绑定、来源会话与事件引用、记录类型、内容、
来源顺序、可见范围，以及可选的修订关联和 checkpoint。应用未提供的信息保持未知，
不得伪造稳定 ID、完整历史或执行终态。应用特有字段由 plugin 解释并保留为来源
引用，不要求核心理解该应用的 session 或 operation 模型。

核心校验绑定与交接 anchor 的关联，持久化记录及去重依据后才推进观察进度。恢复时由
plugin 根据已保存的外部引用和 checkpoint 对账；没有可恢复游标或稳定事件 ID 时，
必须明确保证的范围。记录转换、来源及 Tape 可见性由
[Plugin Integration Spec](plugin-integration-spec.md) 定义。

提交调用返回与外部工作完成是不同事实。Plugin 应说明工作是否被接受；无法确定时
报告不确定结果。在没有可验证幂等契约时，不确定的提交不得自动重发。取消和晚到
结果也必须保留各自事实。

## 演进与验收

变更契约时先定义版本兼容关系，未知必需能力或不兼容版本必须明确拒绝；可选能力
可以缺失。第一版以两个用途的最小公共契约为准，不预先承诺所有应用能提供相同
历史、订阅、幂等或取消保证。

行为实现以 `tests/e2e/features/*.feature` 为验收合同，通过公开 API、真实 HTTP、
临时磁盘和确定性 plugin fixture 验证：多连接隔离、能力缺失、认证失败、插件关闭、
未知投递、重复观察及重启恢复。开发运行 `mise run e2e`，交付运行 `mise run test`。
